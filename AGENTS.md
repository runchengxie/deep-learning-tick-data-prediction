# Repository Collaboration Guide

Read the root README and [docs/README.md](docs/README.md) before changing code. For experiment methodology, also check the relevant paper or source record in this repository.

## Project scope

This repository owns model-specific research on tick, limit-order-book, minute, and other structured market data. The archived FI-2010 reproduction is under `legacy/` and is a reference only. Keep these evidence classes distinct:

- Engineering behavior verified by automated tests
- Experimental settings supported by a paper or official data format
- Numerical findings that require real training results

Results from `ticknet.nextday` are independent of the FI-2010 reproduction. FI-2010 cannot establish that next-day stock ranking works. New results must use real data with security, trading date, and timestamp identifiers, and report out-of-time evaluation. Do not describe results as reproduced or consistent with a paper unless the evidence supports that statement.

## Code ownership

- `src/ticknet/model.py` and `dataset.py` retain compatibility models and synthetic-data helpers. `src/ticknet/train.py` provides shared random-seed, device-selection, and classification-metric utilities.
- `src/ticknet/nextday/` owns next-day labels, sharded datasets, chunked models, cross-sectional metrics, and training. It includes minute HGB, TCN, and GRU baselines plus the raw-order-book research path.
- `src/ticknet/eventstream/` owns lossless L2 event packing, causal Transformer training, and prediction export. Its data contract is defined in `config.py`.
- `src/ticknet/research/` owns the experiment loop: proposals, protocol checks, locked-test isolation, experiment registry, prediction audits, and research agents. It is decoupled from `nextday` through CLI entry points and YAML configuration, and must not import `nextday` implementations directly.
- `scripts/` contains human-run entry points, not reusable business logic.
- `tests/` use synthetic data and must not require Google Drive or the full FI-2010 dataset.
- `legacy/` contains the FI-2010 reproduction reference. It is outside the main quality gate, and production code must not depend on it.

Prefer existing boundaries for new work. If a module discovers data, computes models, and schedules experiments, separate those responsibilities. Locked-test access in `ticknet.research` is enforced in code. Changes to test data or date splits must pass `ResearchProtocol` validation first.

## Research facts to preserve

- FI-2010 model inputs use the first 40 raw order-book features.
- Hand-crafted features in columns 40 through 143 are not model inputs.
- Label columns map to horizons 10, 20, 30, 50, and 100, in columns 144 through 148.
- Setup 1 uses Training and Testing files from the same cross-validation fold.
- Setup 2 trains on CF_7 and tests on CF_7, CF_8, and CF_9.
- Real-data training requires NPY data and metadata generated by the conversion scripts.
- Training must stop when required metadata is missing. It must not silently use a random split.
- Early raw-order-book capacity experiments lock 2025. Current AgentX and event-stream series use 2025 for development and lock 2026.
- `docs/project-status.md` is the current status entry point. A roadmap does not replace it.

## Required local checks

Run these commands after changes:

```bash
pre-commit run --all-files
python scripts/check.py
```

`pre-commit` checks file hygiene, Ruff, `ty`, and notebooks. `scripts/check.py` runs Ruff, formatting, `ty`, pytest with coverage, and a smoke check.

The public synthetic-data CI workflow runs Ruff, formatting, `ty`, pytest with coverage, and Python compilation on pull requests and pushes to `main`. It requires no private credentials, real market data, or GPU. Full training, slow tests, and GPU checks remain manual or on demand. Python 3.10 compatibility and dependency security are outside this workflow. Validate them in Python 3.10 when a change creates a relevant risk.

When changing data protocols, add regression tests for incorrect selections, wrong label columns, and windows crossing files. For checkpoint changes, test resume positions and configuration conflicts. Before documenting a command, confirm its options with `--help`.

## Git and worktrees

Use an isolated worktree for every change. Do not commit directly on `main`.

1. Fetch the repository's actual destination remote.
2. Create a task branch and worktree under the workspace's configured `.worktrees/` directory.
3. Implement and run the checks in that worktree.
4. Commit, push the task branch, open a pull request, and merge only after required checks pass.
5. After merge, confirm the worktree contains no unique unsaved work before cleaning up this task's branch and worktree.

Never bypass branch protections, hooks, or required checks. Preserve unrelated branches, worktrees, and unsaved changes. If a remote or required check is unavailable, keep the recoverable branch and report the limitation.

Worktrees do not include `.venv`. When available, link the task worktree to the repository checkout's existing `.venv` for validation, then remove that link before committing. Do not install or rewrite shared repository hooks from a worktree.

## Documentation language and evidence

Write maintained explanatory documentation in clear English. Keep identifiers, paths, options, schema names, bibliographic titles, and direct source quotations stable where translation would alter them. When translating research records, preserve dates, metrics, samples, assumptions, failed or inconclusive experiments, provenance, and limitations. Link to authoritative source notes instead of duplicating their full evidence.

Keep documents concise and use natural, direct language. Lead with the question, what was tested, what was observed, and what remains uncertain. Do not turn results into promotional claims or remove evidence to shorten a note.

When modifying a command in documentation, check its `--help` output. Documentation changes must run pytest because tests verify local Markdown links and source-preservation rules.

## Data and artifacts

Do not commit FI-2010 data, checkpoints, logs, or generated images. Follow the repository's locked `uv.lock` for dependencies. After modifying `pyproject.toml`, run `uv lock` and inspect the lockfile diff.

Do not modify `docs/references/1808.03668v6.pdf`. Reading notes may be edited for clarity and factual accuracy, but retain the paper's section structure and citation details.

Keep training data, checkpoints, logs, and large artifacts outside Git in the project's designated data location. Production jobs must use stable release paths, never temporary worktrees. Before cleaning a worktree, check that no scheduled job references it.
